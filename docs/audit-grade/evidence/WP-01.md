## Arquitectura resultante

```text
PR o push a main
  -> checks ligeros: workflows, action pinning, invariantes, secretos y unit tests
  -> preflight gate
  -> builds inmutables + Dataform/dashboard/Terraform validation
  -> CI gate del SHA exacto
  -> workflow_run exitoso de un push a main
  -> verificar repo, branch, evento, conclusion y SHA actual de main
  -> environment production y aprobacion independiente
  -> repetir verificacion del SHA aprobado
  -> publicar las ocho imagenes verificadas y resolver digests
  -> crear rama candidata con el tree exacto APPROVED_SHA:dataform
  -> compilar y validar el candidato sin mover dataform-production
  -> capturar release Dataform y trafico Cloud Run completos
  -> compare-and-swap de dataform-production + expansion compatible
  -> staged revision sin trafico -> metadata -> GET /readyz
  -> promover trafico -> GET /healthz
  -> guardar evidencia o restaurar release, rama y trafico exactos
```

`.github/workflows/ci.yml` se ejecuta para `pull_request` hacia `main`, `push` a `main` y `workflow_dispatch`. Sus jobs usan permisos read-only. Los Docker builds dependen de `preflight-gate`, por lo que no comienzan antes de validar workflows, invariantes, secretos y tests.

`.github/workflows/deploy.yml` no acepta `pull_request`, `push`, `master` ni `workflow_dispatch`. Solo consume un `workflow_run` exitoso de `CI` cuyo evento original fue un push a `main`, desde el mismo repositorio, y cuyo `head_sha` sigue siendo el SHA remoto actual de `main`. El deploy permanece deshabilitado y no fue ejecutado.

`deploy-dashboard.yml` aplica el mismo contrato para `workflow_run`: rechaza otro repositorio, CI fallido, evento distinto de push y SHA obsoleto. Repite la consulta del SHA remoto inmediatamente antes de `actions/deploy-pages`.

## Invariantes de seguridad

`verify_repo_invariants.py` falla cerrado ante `PAPER_CHAMPION`, modos LIVE, ejecución real, Strategy Brain fuera de `BACKTEST_ONLY`, `production_change_allowed=true`, schedulers Strategy Brain reactivados en el baseline, deploy desde `master`/PR/push directo/dispatch, secretos de alta confianza, eliminación del lock legacy o resultados `LEGACY_PRE_AUDIT_GRADE` elegibles para promoción. La ejecución real produjo `REPO_INVARIANTS_VALID` y las pruebas negativas exigen exit code no cero.

## Build once e identidad

CI construye ocho imagenes desde `scripts/ci/cloud_run_services.json`. Cada artifact conserva SHA Git, image ID, `image.tar.gz` y checksum. Deploy descarga artifacts del run exacto, comprueba checksum/SHA, carga la imagen y compara el image ID real de Docker con `metadata.json`; metadata manipulada falla. Publica una vez y despliega exclusivamente por digest `@sha256:`.

Todas las GitHub Actions estan fijadas a commits SHA completos. Actionlint esta fijado a un digest Docker `sha256`. `verify_action_pinning.py` y sus tests rechazan tags y referencias mutables.

## Promocion Dataform transaccional por referencia

Despues del approval y de volver a validar el SHA de `main`, el workflow captura `previous_dataform_production_sha`, crea un commit cuyo tree es exactamente `APPROVED_SHA:dataform` y publica solo `dataform-candidate-<sha>`. `dataform-production` permanece inmovil durante preparacion y compilacion. La compilacion debe declarar esa rama candidata, resolver al commit exacto y contener cero `compilationErrors`.

La promocion usa compare-and-swap con `--force-with-lease` contra el SHA anterior. Si otra ejecucion mueve la rama, falla cerrado. Solo despues del CAS se actualiza `releaseCompilationResult`; la evidencia registra SHA anterior, candidato y final, tree SHA, compilation ID, release anterior/nuevo y metadata de rollback. Cualquier fallo posterior restaura primero el release y despues la rama mediante otro CAS; ambos rollbacks son idempotentes y rechazan estados concurrentes desconocidos.

Las pruebas directas cubren fallo tras crear candidato, fallo de compilacion, fallo posterior al movimiento, cambio concurrente, rollback conjunto de release/rama e idempotencia. Esta promocion no se ejecuto contra Dataform production durante el PR.

## Contrato expand/contract

No existe una transaccion distribuida entre Dataform, BigQuery y Cloud Run. La seguridad de transicion se obtiene imponiendo una expansion compatible primero y promoviendo Cloud Run despues. `runtime_compatibility.json` conserva contratos `legacy` y `current`; CI rechaza eliminaciones, renombres, cambio de tipo, `CREATE OR REPLACE`, columnas legacy ausentes o una fase `contract` dentro de la misma release. Las eliminaciones deben ocurrir en una release posterior, cuando no exista ningun consumidor legacy.

El contrato y sus pruebas demuestran que el codigo anterior y el nuevo disponen simultaneamente de sus columnas durante la transicion. Esto prueba compatibilidad versionada, no atomicidad distribuida.

## Smoke funcional no mutante

`smoke_test_services.py` conserva como primera capa `gcloud run revisions describe`: exige `Ready=True`, generacion observada e imagen igual al digest aprobado. Como segunda capa obtiene un identity token con audience explicita para servicios privados y ejecuta solo `GET /readyz` sobre la revision staged y `GET /healthz` despues de promover trafico.

Cada servicio expone ambos probes antes de cargar configuracion de negocio. `/healthz` es liveness estatico. `/readyz` valida con timeout metadata de release, imports, presencia de secretos sin exponer valores, tablas esenciales mediante `get_table`, `PAPER_EXECUTION_MODE=paper`, URL Alpaca exactamente `https://paper-api.alpaca.markets` y Strategy Brain `BACKTEST_ONLY`. No crea ordenes, no ejecuta estrategias, no escribe BigQuery, no envia alertas y no modifica recursos.

Las pruebas cubren HTTP 200, HTTP 500, timeout, SHA/digest incorrectos, respuesta malformada, intento de operacion prohibida y autenticacion privada. Ademas, las ocho imagenes se iniciaron con filesystem read-only y sin credenciales: cada una produjo `/healthz=200`, `/readyz=200` con fixtures read-only y `/readyz=503` al retirar configuracion. No se llamo ningun servicio live.

## Rollback exacto

Antes de crear revisiones, `cloud_run_traffic.py` captura `spec.traffic`, `status.traffic`, revisiones, porcentajes, tags, `latestReadyRevision` y `latestCreatedRevision` de cada servicio. El artifact se conserva aun cuando falle el workflow.

El rollback opera en orden inverso y se construye desde `spec.traffic`, conservando `latestRevision=true`, revisiones explicitas, porcentajes y tags. Despues de cada comando vuelve a ejecutar `gcloud run services describe` y compara `spec.traffic`, `status.traffic`, tags y porcentajes con el snapshot. Un comando exitoso con estado remoto parcial sigue siendo fallo. La verificacion post-restore queda en el artifact.

Si la promocion termina pero GitHub no puede retener el artifact de evidencia, un paso protegido por `failure()` restaura tambien el release Dataform y todo el trafico previo; una promocion sin evidencia auditable no queda activa.

Las pruebas cubren `latestRevision=true`, 100/0, 90/10, multiples tags, estado remoto incorrecto tras comando exitoso, restauracion parcial, fallo de describe/verificacion, varios servicios e idempotencia. Falta un drill live autorizado, por lo que OP-05 permanece `PARTIAL`.

## Dependencias

CI ejecuta `npm audit --json` para dashboard y Dataform y aplica `npm_audit_gate.py` con umbral critical fail-closed. No existe excepcion global por severidad. La allowlist versionada identifica cada advisory autorizado por GHSA/CVE, paquete, version, superficie, razon, owner, issue de remediacion y expiracion; falla ante advisory nuevo, excepcion expirada/incompleta o cambio de paquete/version.

Dataform conserva deuda critica heredada de `vm2@3.9.19`: 20 registros exactos autorizados temporalmente hasta `2026-09-30`, con seguimiento exclusivo en [Issue #52](https://github.com/MauroTravisany/firstlayer_stock_market/issues/52). El gate exige que el issue permanezca abierto y rechaza excepciones vencidas, duplicadas, sin finding correspondiente o cuyo paquete/version cambie. Dashboard no tiene findings critical autorizados.

Dependabot cubre GitHub Actions, npm de dashboard/Dataform, Terraform y pip `/` para `requirements-ci.txt`.
